# Clarity Landing Home Page Section Outline

Status: Phase 2 home page section order approved for initial landing launch.

Purpose: define the `/` information hierarchy so the landing page feels professional, mobile-friendly, and Plaid-review ready.

## Home Page Section Order

1. Hero
2. Trust Bar
3. Problem
4. Features
5. Plaid & Data Consent
6. Screenshots / Product Proof
7. FAQ
8. Final CTA

## Section Details

### 1. Hero

Purpose: explain Clarity in one glance.

Required content:

- Product name: Clarity
- Core positioning: personal AI financial co-pilot
- Rex positioning: Rex is the assistant inside Clarity
- Primary CTA: Join the beta / Request access
- Secondary CTA: Read how data is handled

Copy constraints:

- Do not imply Clarity is a bank.
- Do not imply Plaid endorses Clarity.
- Do not make guaranteed financial outcome claims.

### 2. Trust Bar

Purpose: immediately lower user and reviewer concern.

Required content:

- User-authorized account connection
- Privacy-first data handling
- Clear disconnect and deletion path
- Account connection through Plaid

Copy constraints:

- Keep claims concrete.
- Avoid unsupported certifications or security absolutes.

### 3. Problem

Purpose: describe the real pain Clarity solves.

Required content:

- Personal finance data is scattered.
- Budgets, transactions, and spending decisions are hard to interpret manually.
- Users need context-aware help without handing over control.

Copy constraints:

- No fear-based copy.
- No "we fix your financial life" claims.

### 4. Features

Purpose: show what Clarity does in practical terms.

Required content:

- Transaction organization
- Budget tracking
- Rex chat and voice assistance
- Memory/goals context
- Spending insights

Copy constraints:

- Each feature must map to implemented app behavior.
- Use simple benefit-led language.

### 5. Plaid & Data Consent

Purpose: make the account connection model clear before users join.

Required content:

- Clarity uses Plaid to let users connect financial accounts.
- Connected data may include accounts, balances, transactions, and institution metadata depending on permissions.
- Clarity uses this data for budgeting, categorization, insights, and Rex context.
- Users can disconnect accounts and request deletion.
- Links to Privacy, Security, and Data Deletion.

Copy constraints:

- Use neutral Plaid integration language.
- Do not present Plaid as a sponsor or endorsement.

### 6. Screenshots / Product Proof

Purpose: prove the product exists and help reviewers understand the use case.

Required content:

- Dashboard or budget screenshot
- Rex assistant screenshot
- Optional transaction organization screenshot

Copy constraints:

- Use synthetic or redacted data only.
- Screenshots must be current and visually polished.

### 7. FAQ

Purpose: answer predictable trust questions without bloating the page.

Required questions:

- What is Clarity?
- Who is Rex?
- What financial data does Clarity access?
- How does account connection work?
- Can I disconnect or delete my data?
- Is Clarity financial advice?
- How do I contact support?

Copy constraints:

- Keep answers short.
- Link to detailed policy pages.

### 8. Final CTA

Purpose: convert interested users after trust and consent are explained.

Required content:

- Request access / Join beta form anchor
- Short reassurance that no bank credentials are collected by the waitlist form
- Contact link for privacy or support questions

Copy constraints:

- Do not request sensitive financial data.
- Do not imply instant production bank connection availability.

## Mobile Layout Rule

The first viewport should show:

- Clarity name
- Clear headline
- Short supporting copy
- Primary CTA
- A hint of the next trust section

Avoid:

- Oversized hero that hides trust content.
- Dense legal copy in the hero.
- Tiny screenshots that cannot be inspected on mobile.

## Implementation Notes For Later Phases

- The Plaid/data consent section should appear before screenshots if screenshots show financial data.
- Footer compliance links must appear on the home page and every public route.
- The waitlist/request-access form should live near the final CTA or as a short embedded section after the hero and repeated at the bottom.
